Technical Memo Engineering Work Summary – Distributed Systems, Networking, and Security Author: Michael Kamensky Background: B.S. Computer Engineering, UC Santa Cruz Executive Summary This memo documents two major engineering efforts: Redesigning a stateful reverse tunneling proxy system in Kubernetes to enable horizontal scaling and eliminate a production bottleneck (Industry – Dymium). Designing and implementing a QUIC protocol fuzzing framework to evaluate firewall behavior on encrypted transport traffic (Academic Research – UCSC). Both projects required working under real-world constraints, navigating ambiguity, and designing systems where correctness, reliability, and security were critical. The common theme across these efforts is distributed systems design under constraint and adversarial or high-stakes environments. Part I: Scalable Reverse Tunneling Architecture (Dymium) Problem Context Dymium operates infrastructure that requires secure access to customer databases that are typically located behind firewalls. To support this, the system relied on a stateful reverse tunneling proxy architecture. The architecture included: Connector components deployed on the customer side of the firewall A Mesh Server component running inside Kubernetes Long-lived TLS connections between components Customer-specific routing requirements The system had a critical limitation: The Mesh Server operated as a stateful pod and could not be horizontally scaled due to connection ownership and routing constraints. This created a production bottleneck and reliability risk. Core Technical Challenge The challenge was to enable horizontal scalability without: Breaking existing TLS connections Modifying customer-side components Redesigning the entire system architecture Violating strict routing correctness The problem was fundamentally one of: Stateful distributed coordination Connection ownership management Safe traffic routing in Kubernetes Architectural Solution 1. Connector Failover Logic On the customer side, I contributed to logic that enabled: Multiple connectors to exist simultaneously Rapid takeover if a primary connector failed Preservation of routing correctness This introduced resilience at the edge of the system. 2. DNS-Based Routing Layer To address Mesh Server scaling constraints, I designed a custom DNS-based load-balancing layer deployed inside Kubernetes. Key components: A custom DNS server deployed as a Kubernetes Service Workloads configured via ConfigMaps to use this DNS server Proxy-reported state via API calls Zero-TTL DNS responses to ensure real-time routing decisions Instead of traditional stateless load balancing, the DNS server: Maintained a mapping of customer connections to specific Mesh instances Used proxy-reported metadata to determine routing Returned routing decisions dynamically This enabled: Horizontal scaling of previously single-instance components Preservation of connection ownership Controlled failover without violating state assumptions Why DNS Was Chosen DNS provided: Lightweight routing indirection Minimal change to existing application logic Compatibility with Kubernetes-native infrastructure Real-time routing control via zero-TTL records The design avoided intrusive architectural changes while introducing scalable coordination. Engineering Constraints The work required navigating: Stateful TLS sessions Kubernetes pod lifecycle behavior Routing determinism requirements Production reliability expectations Limited ability to change upstream components This was a system redesign under heavy constraints, not a greenfield rewrite. Lessons Learned Horizontal scaling of stateful systems requires indirection layers. DNS can serve as a distributed coordination primitive when used carefully. Production systems require correctness first, scalability second. Ownership means solving problems within constraints, not replacing the system. Part II: QUIC Firewall Fuzzing Framework (UCSC Research) Research Context The goal of the research was to evaluate: How do firewalls handle QUIC traffic, and can protocol-level mutations evade filtering? QUIC presents unique challenges: Encrypted transport Complex handshake logic Token-based validation Evolving protocol specifications The research required building a protocol-aware fuzzing framework, not random mutation. Technical Challenges 1. Generating Valid QUIC Packets Attempts included: Writing a packet generator from scratch (difficult due to handshake token requirements) Modifying existing high-level QUIC libraries (insufficient low-level control) The challenge was balancing: Validity Mutability Control over specific protocol fields Final Approach The solution was to design a wrapper-based mutation pipeline: Capture valid QUIC packets. Parse protocol-level structure. Apply targeted, protocol-aware mutations. Replay mutated packets against firewall-protected targets. Record and analyze evasion outcomes. This approach ensured: Baseline protocol correctness Controlled mutation strategies Reproducible experimental methodology Research Outcomes The framework allowed systematic evaluation of: Evasion vs non-evasion cases Firewall behavior consistency Handling of encrypted transport traffic Results were analyzed and synthesized into a written research paper examining firewall handling of QUIC traffic. Engineering Takeaways Protocol-level reasoning matters more than brute-force fuzzing. Testing adversarial systems requires structured methodology. Observability and logging are as important as mutation logic. Engineering rigor and research rigor are closely related disciplines.Part III: Re-Architecting a Monolithic Search Engine (MarchUp) Context MarchUp is a social media platform whose search functionality was embedded directly within its PHP/Apache web server stack. The original architecture: Search engine logic ran inside the PHP web server Search state was tightly coupled to application state Scaling the web server implicitly scaled search Real-time indexing was limited Horizontal scaling was constrained by shared state and monolithic design This coupling created: Performance bottlenecks Limited scalability Tight state dependency between web tier and search logic Architectural inflexibility The goal was to explore how the search engine could be decoupled from the monolithic web server and redesigned as a horizontally scalable system. Core Problem The search engine was: Embedded in the web application layer Dependent on in-process state Not independently scalable Difficult to modify without impacting the entire application The architectural challenge was: How do you extract a stateful search subsystem from a monolithic PHP web server and redesign it as a scalable, distributed service? Architectural Strategy Step 1: Decoupling Search from the Web Server The first architectural goal was removing search logic from the PHP web server. This required: Identifying implicit state dependencies Defining clear API boundaries Designing a service-oriented interface Separating indexing logic from request handling The objective was to make search: Stateless at the web layer Independently deployable Horizontally scalable Step 2: Prototyping AWS-Based Architectures I designed and evaluated multiple AWS-based prototypes to test distributed search architectures. Key technologies explored: AWS Lambda for serverless query processing Amazon OpenSearch for scalable indexing and retrieval Cloud-native scaling patterns Asynchronous indexing workflows Each prototype explored tradeoffs between: Real-time indexing latency Query response time Infrastructure cost Operational complexity Consistency guarantees Real-Time Indexing Prototype One advanced prototype introduced: Decoupled indexing pipelines Event-driven updates Near real-time search freshness Independent scaling of indexing vs query workloads This improved upon the original architecture, where search updates were tightly coupled to web server processes. The prototype demonstrated: Improved scalability Better separation of concerns Reduced coupling between application and search logic Greater architectural flexibility Engineering Challenges The work required: Understanding legacy PHP architecture Identifying hidden state dependencies Designing clean service interfaces Evaluating cloud-native scaling tradeoffs Balancing performance with cost constraints Because this was exploratory architecture work, success meant: Designing viable scalable alternatives Evaluating performance characteristics Producing actionable design proposals Lessons Learned Monolithic systems often hide state in unexpected places. Decoupling requires careful interface design, not just code movement. Serverless architectures introduce new tradeoffs (cold starts, event timing, cost modeling). Search systems benefit from independent scaling and event-driven indexing. Prototyping multiple architectures clarifies tradeoffs better than debating them abstractly.
